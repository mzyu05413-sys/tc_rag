# P2.9：RAG 质量评估与验收

[返回 P2 总览](README.md)

## 评估回答什么

RAG 是否找到更完整的依据、是否改善用例，额外耗时/token 是否值得？用例变多或自动关联全部连上，不能单独证明效果变好。评估只读 SQLite，不调用模型，不自动猜测语义匹配。

## 金标格式

每次运行的规则、测试点、用例和相关证据 ID 不同，需按该运行标注。以下都是虚构 ID，使用前必须替换：

```json
{
  "rules": [{"rule_id": "gold-300", "statement": "最多300个，数量为整数。"}],
  "rule_groups": [{"generated_ids": ["运行中规则ID"], "gold_ids": ["gold-300"]}],
  "relevant": {"retrieval中的query_id": ["相关证据ID1", "相关证据ID2"]},
  "manual": {
    "covered_gold_rule_ids": ["gold-300"],
    "covered_point_ids": ["人工确认已正确覆盖的point_id"],
    "unsupported_case_ids": [],
    "duplicate_case_ids": []
  }
}
```

rule_groups 人工确认语义对应，支持一对多/多对一；同规则不得在多个组重复计数。缺失 rule_groups 表示未评估，显式空列表表示已评估但无匹配。relevant 是某查询应召回的证据集合，不能用空列表冒充未知。未标注指标输出 null。

manual 中 covered_gold_rule_ids 指有效用例正确覆盖的金标规则；covered_point_ids 指人工确认有效覆盖的本次测试点；另外两项为全量人工检查后的无依据/重复用例集合。只抽查部分时不要把未检查用例视为通过，暂不填这些全量指标。

## 评估命令

```powershell
tc-rag evaluate RUN_ID --gold workdir/gold-for-this-run.json --k 10 `
  --config workdir/local.yaml --output workdir/eval/rag.json
```

按总览执行一次完整生成，再为本次运行标注金标并执行 evaluate；评估标注不是中间审核门槛。
检查召回的遗漏条件、无依据预期、重复及覆盖；不要把用例数量增长当作质量增长。

报告保存配置、输入指纹、输入与生成指令、提示词版本及指纹、阶段耗时、实际调用和 usage。
评估仅处理已有结果，不发起模型请求，不替人工判断业务正确性。

## 系统质检（不调用模型）

```powershell
rag quality RUN_ID --config workdir/local.yaml
rag quality RUN_ID --config workdir/local.yaml --strict
```

只读运行快照，逐阶段输出 `pass / warn / fail / not_applicable`，默认写入运行产物目录的
`reports/quality_check.json` 和 `.md`。`fail` 退出码 2；`warn` 默认不阻断，`--strict` 时也退出 2。
命令不创建模型客户端，不重新解析，不改写 SQLite。

检查覆盖：运行/文档指纹；图片与 vision Block 配对；分块区间、文本拼接、覆盖、预算与跨页续表表头；
引文回查与规则引用闭包；测试点边界完整性；纯界面展示点是否已按功能概括；用例步骤引用、覆盖关联、
重复与无依据数字；索引/检索范围与采用/省略记录；失败调用与 usage；快照密钥排除；
`semantic_review` 必须保持 `not_performed`。缺少阶段记 `not_applicable`，不写成通过。

自动检查只证明已保存事实的结构和引用关系，不证明需求语义正确。人工语义结论仍由
`rag evaluate` 的金标和人工抽查给出，两者不能互相替代。

### 怎样检验质检本身

1. 对已完成运行执行 `rag quality RUN_ID`，打开 `quality_check.md`；每条检查应有阶段、状态、
   计数和对象 ID，失败项能在 `rag inspect RUN_ID --stage <stage>` 或 SQLite 中复现。
2. 用虚构快照逐项注入错误引用、越界区间、缺失边界点、重复用例、无依据数字、范围外检索 ID、
   失败调用；对应检查必须失败/警告，干净对照必须 0 fail。
3. 没有人工金标时，`rag evaluate` 的 precision/recall/召回/人工覆盖应为 `null`，不是 0；
   抽查 3 条自动通过项，人工确认语义，不一致时以人工结论为准并记录。

`tests/unit/test_quality.py` 与 `tests/integration/test_quality_cli.py` 覆盖干净对照、
已知缺陷注入、缺阶段、退出码和“质检不调用模型”。

## 指标与验证

| 指标 | 含义 |
|---|---|
| rule_precision / rule_recall | 基于人工匹配组，按两侧唯一规则计数 |
| evidence_recall_at_k | 有人工相关性标注查询的宏平均证据召回 |
| automatic_rule_link_ratio / automatic_point_link_ratio | 自动有效关联比例，不是人工正确率 |
| flagged_expectation_ratio | 启发式标出的可疑预期比例，不是完整幻觉率 |
| manual_gold_rule_coverage / manual_point_coverage | 人工确认的业务覆盖 |
| manual_unsupported_expectation_ratio / manual_duplicate_case_ratio | 人工确认的无依据预期/重复比例 |
| gap_count / conflict_count / duplicate_issue_count | 问题清单统计，保留自动校验局限 |

`test_evaluation.py` 验证规则组匹配、缺标注及人工/自动分离；`test_rag_cli.py` 用虚构需求和预设模型跑通 RAG、审核、生成及 evaluate，并验证重排配置开关。离线结果不能写成真实收益。

真实验收需记录：rag 是否找回遗漏条件/例外、有无错误解释；有效覆盖、无依据预期、重复率的变化；rerank 是否进一步改善；耗时/token 是否可接受；两个后端的结果及实测性能。未做这些检查前，状态为“代码与离线验证完成，业务效果待验收”。真实报告和标注保留在被忽略的 workdir/eval。
