# P2.6：上下文与生成

[返回 P2 总览](README.md)

## 直接证据和补充证据

直接证据按规则 ID 加载，包含所属功能的相关规则及条件/例外，不依赖 top-k 或阈值。RAG 额外提供 supplemental_evidence：同文档其他规则引文、原文片段或带来源的图片解释。

只有一条 RAG 流程，规划和生成始终保留 schema、审核门槛及依据校验。`prompts/rag_context/v1.md` 区分规则绑定的原文依据与检索补充材料，要求冲突和不确定内容进入问题。

## 预算和事实保存

`Pipeline._generate_batch()` 先检查核心请求及输出 schema 的预算，过大则拆测试点批次；单点仍过大则失败。`_supplement()` 按排名加入补充证据，超预算从末尾逐条省略。

**核心规则和直接证据不会因 RAG 超预算而被静默删除。** 测试点规划阶段尚不支持任意原子规则自动拆分，核心请求过大会报错。

最终 ContextBundle 保存到 context_bundles 和运行 retrieval 快照：原始命中、直接证据、adopted_ids、omitted_ids、分数、选择原因、模型/schema/预算。manifest 另存完整配置和提示词指纹。

cases 读取同一运行的 SQLite 测试点、规则和分块快照，校验文档、规则引用与配置，重建并校验索引。用例每步只可引用所选测试点允许的规则，以及这些规则绑定的证据。补充片段不会自动加入引用闭包。内置及可选自定义 Skill 只追加到生成提示词，其指纹进入缓存依赖，不作为业务证据。

## 验证和限制

`test_supplement_is_adopted_and_budget_omission_is_auditable` 验证补充材料确实进入请求且省略有记录；连续流程测试验证规划和生成都检索。跨批引用拒绝、独立边界 299/300/301 等回归继续运行，已移除旧审核绑定测试。

若检索发现可能遗漏的新规则，先形成待确认信息；经人工修正规则或重新提炼后再进审核链，不在生成期间悄悄扩展需求范围。
