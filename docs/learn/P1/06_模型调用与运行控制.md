# P1.5 模型调用与运行底座

[返回学习导航](../README.md) · [P1 总览与完整命令](01_功能架构与流程.md)

## 先理解目的

业务服务不应自己处理 SDK、网络错误与密钥。

## 输入和输出

模型请求和输出类型 → 经过 Schema 校验的 ModelResult。

## 处理流程与代码阅读

显式选择 Chat Completions/Responses；信号量限制并发；逐次请求计数；限流与临时错误有限重试，认证失败快速停止，JSON 结构错误有限修复。

提炼、测试点规划和用例生成均由固定数量的工作协程提交批次，数量由
`models.llm.concurrency` 决定。提炼在整组请求通过预算预检后启动；规划、生成在各批
检索补充后检查完整输入预算。完成顺序可以不同，归并顺序保持原文和测试点顺序。
某一请求失败或用户取消时，先取消并等待其余工作协程，再保存失败状态。

结构修复携带契约字段路径、类型、枚举或版本常量，帮助模型纠错；不重放错误输出和任意
未知字段名。严格 Schema 与证据校验保持不变。提炼失败后显式恢复时，配置、指令、文档
校验一致，才会复用父运行中请求指纹匹配的成功批次；失败或截断的结果不会作为缓存。

`response_format` 区分远端 `json_schema` 和兼容服务的 `json_object`；后者仍传完整输出契约，
并保留本地 Schema 和证据校验。`thinking_mode` 默认不发送，只对支持该字段的 Chat 服务显式配置。
完整操作见 [终端交互与调试](13_终端交互与调试.md)。

先读 `src/tc_rag/infrastructure/providers/openai_sdk.py` 的入口及中文注释，再沿其调用进入端口和领域模型。文件路径从项目根目录起算。

## 用一个例子理解

HTTP 429 后重试会产生两条调用记录；未知 token 是 null，不是0。

## 验证和审核

自动验证见 `tests/integration/test_provider.py`。审核时沿“原文 → 规则 → 测试点 → 步骤预期”反向查一次，确认每个结论都能找到输入依据。

## 当前边界

Schema 正确不等于业务正确；真实调用须自行明确启用。max_cost 尚无价格表，不能伪造金额预算。
