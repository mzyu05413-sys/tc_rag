# P1.7 测试点设计

[返回学习导航](../README.md) · [P1 总览与完整命令](01_功能架构与流程.md)

## 先理解目的

测试点描述要检查什么，不是具体操作步骤。

## 输入和输出

规则与证据 → 程序规划的测试点 + 模型补充的具体测试意图。

## 处理流程与代码阅读

规则种类映射设计方法；Decimal 推导明确边界；模型补充业务意图但不得另猜数值边界。精度未知或条件冲突时进入待澄清。

纯界面展示点：规则全部为 `other`、证据全部来自 `vision`、无结构化约束且只描述可见外观时，
同一功能合并为一条“<功能>：界面展示汇总”概括点；单点也改写。原规则和证据引用保留在汇总点及
Excel 附表。`planning.ui_display_policy=keep` 可保留旧行为；合并是确定性后处理，不调用模型。

随后 `planning.vision_policy=aggregate` 默认将普通纯图片点汇总为待补文字依据的信息问题，
展示汇总点保留，纯图片边界点保留但降为 `needs_context + undetermined`。
`downgrade` 保留普通纯图片点并降为待补上下文，`keep` 保留原点。
最终只为 `ready + applicable` 的点生成用例；脑图的全部点指上述策略处理后保存的点。

先读 `src/tc_rag/application/services/design.py` 的入口及中文注释，再沿其调用进入端口和领域模型。文件路径从项目根目录起算。

## 用一个例子理解

上限300且为整数 → 299/300/301三个独立点；精度2的3.00 → 2.99/3.00/3.01。

## 验证和审核

自动验证见 `tests/unit/test_design.py`。审核时沿“原文 → 规则 → 测试点 → 步骤预期”反向查一次，确认每个结论都能找到输入依据。

## 当前边界

开闭比较符决定通过/拒绝预期，三个候选值不代表都合法。待澄清点暂不生成正式用例。
界面展示合并只处理明确的 vision 外观证据；被错误标成功能规则的展示内容仍需提示词和人工纠正。
