# R0～R3 评测流程指南

版本 v1.1，日期 2026-11-12。实验定义见[实验方案](retrieval_experiment_plan.md)。本指南把人工准备、开发和实际跑实验分开登记。

## 1. 今天先准备什么

用户先完成以下三项，不需要重新入库。

1. 查看并提供当前已发布 snapshot_id。
2. 从审批流问题草稿选前 5 题，审核问题、相关原文和全部必要证据，按最小事实写引文。
3. 确认这是 15～20 题试点评测，主指标先用 Recall@5/10、MRR@10，综合 F1 用于解释统计口径。

当前可用的查看命令如下。

```powershell
.\.venv\Scripts\python.exe -m tc_rag.interfaces.cli kb list cordys
# 需要复制结构化快照信息时
.\.venv\Scripts\python.exe -m tc_rag.interfaces.cli kb list cordys --json
```

若没有发布快照，先处理入库问题，再继续 R0。已有快照不为实验主动重跑图片。

助手同期开始 R3 的计数、宏/微汇总和手算单测。R3 完成前不跑三模式正式指标。

## 2. 按阶段协作

| 步骤 | 助手交付 | 用户动作 | 进入下一步的条件 |
|---|---|---|---|
| A 指标 | C/U/G/k、逐题及宏微汇总、边界测试 | 确认定义及零分母处理 | 手算和重复/多证据反例通过 |
| B 只读导出 | 快照、片段、来源、文档向量、查询向量清单 | 提供快照号，缺向量时决定是否补采 | ID/维度/哈希匹配，材料包完成 |
| C 五题试标 | 引文区间转换、格式校验、待决问题表 | 核对五题证据完整性和相关度 | 人工确认，不把预筛当金标 |
| D 扩为试点 | 15～20 题草稿、分层与 query_family | 完成标注，明确 scope_complete 与 reviewed | 金标版本和协议冻结 |
| E R1 | 同一个 harness 跑三模式，输出逐题、评分表与分布 | 审核候选相关性、答案要点覆盖及改善/变差案例 | 三模式输入指纹相同，失败与未知单列 |
| F R2 | 两后端与两测量路径、预热/重复及内存统计 | 确认可运行规模和测量环境 | 结果容差及性能边界可解释 |
| G 报告 | 指标表、配对差值、案例、复现附录 | 复核结论与局限 | 结论能追溯到对应题和记录 |

R1/R2 harness 计划放 eval/kb，算法继续从 src 导入。本文件只列已有真实命令；待开发入口交付并测试后再补操作命令。

## 3. 人工如何填写

当前首批标注请只填写[五题测试点证据标注稿](../../workdir/kb/evaluation/annotations/approval_testpoints_v2/开始标注.md)（2026-11-14）。其中提供候选摘录和中文填写栏，人工无需填写技术 ID；原审批流问题阅读稿保留作历史草稿。当前五题均为面向测试点生成的需求证据检索，用例阶段待固定测试点和代码复用边界核对后再开展。

该稿绑定用户提供的目标快照，但旧摘录到当前快照的 Block、解析版本与偏移映射尚待核验；候选全部 pending，不能视作已审核金标。以下详细字段由助手根据人工反馈整理，不要求人工直接填写。

逐题反馈可以使用普通文本，无需自己计算偏移。

```text
题号：approval_pilot_01
问题：保留 / 修改后内容
查询类型：精确术语 / 自然语言改写 / 多证据联合
查询范围：审批流文档 / 指定其他文件 / 六份全库
必要事实1：原文 + Block ID
必要事实2：原文 + Block ID（有则填写）
答案要点：逐项写出问题必须回答的事实，并对应上述原文
替代证据：同一事实在其他位置的等价表述（有则填写）
辅助背景：原文 + Block ID（有则填写）
是否查全：已查完整指定范围 / 尚未查全
版本冲突或疑问：
审核人：
```

必要事实之间分别计数，替代证据放同一个单元；只提供背景而不能支撑答案的内容不能标成必要证据。助手将原文映射为 content_sha256、原始 Block ID 和 [start_char,end_char)，回交你核对。图片派生内容须能回看原图，来源维持 vision。

如果问题实际没有答案或有版本冲突，明确记录，不按经验填写规则。首批五题先验证规范，尚未查全时保持 pending。R1 金标需要指定范围的完整相关证据；只审核某个模式给出的前几条候选不能宣称完整召回金标。

### 模式结果出来后再审核两项语义分数

先完成上述独立金标，再拿到每种模式的实际候选。每个结果的审核单独保存，不能修改金标来适应模型结果。可用以下格式反馈。

```text
题号：
结果运行 ID：
模式与 k：
候选 chunk_id 1：相关性 0 / 0.5 / 1，理由
候选 chunk_id 2：相关性 0 / 0.5 / 1，理由
必要要点 1：覆盖 0 / 0.5 / 1，对应候选或缺失条件
必要要点 2：覆盖 0 / 0.5 / 1，对应候选或缺失条件
是否审核完整：
审核人：
```

相关性逐候选判断“是否帮助回答”，覆盖逐要点判断“前 k 个片段合起来是否提供必要信息”。不评价生成回答的语言质量。未判断填待审核，不填 0。候选或要点未审完则该题对应汇总保持未知。

相关性没有实际候选时记 null 并计入空结果数；有答案要点但无候选时覆盖为 0。与其他模式比较时核对同一有效题集。评分争议保留原值、理由和仲裁记录，先用五题统一尺度再扩为试点。

## 5. R1 实际跑之前检查

- 三模式的 snapshot、chunk 行序、查询文字、范围与 k 相同，重排关闭。
- 查询向量与文档向量属于同一空间；缺失向量记录为缺失，不自动补模型请求。
- KeywordIndex 的词频实现和 jieba 版本写入清单，RRF 常数 60。
- 关键词构建与稳态查询分别计时，模型调用耗时不混入离线搜索计时。
- reviewed 和 scope_complete 的有效集合冻结；失败、无答案、未知另表。
- 独立金标的答案要点已冻结，再对各模式候选做人工语义审核；量表与覆盖单位一致。
- 语义评分属于本轮人工审核工作，自动汇总工具待开发，不自动发起 LLM 评审。

结束后至少解释一个改善题、一个变差题或确实未观察到变差的事实，以及一个失败案例。没有观察到某种现象时如实报告，不为凑结论编造。

## 6. R2 实际跑之前检查

- 先查 FAISS 是否安装，缺依赖时标记未测，必要安装按项目依赖流程处理。
- 用真实快照矩阵验证，再按内存条件扩到合成规模；维度与归一化保持明确。
- 原适配器与预构建 native Flat 分表，不能只挑更快路径作为系统结论。
- 固定线程、dtype、随机种子、预热和重复次数，记录可用内存及峰值。
- 分数按 ID 对齐，近似并列与 k 边界使用事先登记的容差；比较失败不自动归因语义质量。

## 7. 最终交付给导师什么

报告按实验目标、语料与金标、R3 指标验证、R1 分层结果、R2 两路径结果、失败案例、限制及复现附录组织。问题数、有效数、排除数都展示；性能合成数据与真实质量结果分开。

R1 额外并列展示人工相关性和答案要点覆盖，附五档分布、低分及分歧案例。保持证据定位指标与语义评分各自可解释，避免合并总分。直方图的区间边界和空值数量按实验方案登记。

试点报告可以给出“在这批题上观察到的差异”，暂不宣称默认配置已普遍最优。完整金标未交付前，报告模板和工程验证记录可以先完成，业务数值保留待测。
