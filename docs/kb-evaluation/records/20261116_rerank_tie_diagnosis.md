# 重排退化归因：精确同分与次序

## 发现

用户要求继续分析正文重排退化题，阈值方案暂缓。本轮只离线读取已有dev结果，没有调用模型、改金标或修改生产排序。

`official_approval_39`的两个相关正文片段在原混合排名第1、3位，正文重排后为第17、16位。然而二者的模型返回分数都为1.0，与重排前17位的其他15条完全相同。前排负例涉及审批权限、审批节点、操作日志等相邻主题，没有直接支撑列表管理操作。

因此，先前将16/17名直接解读为“模型认为证据明显较差”不够准确：这道题存在17条最高分并列，最终名次还受到同分顺序影响。长片段和短片段均出现该现象，不能单归因为长文本。

## 工程链路核对

- HTTP适配器按服务返回的`index`映射候选，要求索引完整、不重复、不越界；本轮候选ID和分数映射检查通过。
- 适配器用Python稳定排序按分数降序排列，所以同分时沿用**服务响应行顺序**，没有显式回到原召回排名。
- 本地适配器和采集脚本没有舍入模型分数；1.0是保存的返回分数。无法仅凭现有记录判断远端是否做了截断、量化、舍入或其他处理，也不能证明同分候选内部顺序完全随机。
- dev11题中，6题最高分存在并列，4题同分组跨过k=5截断边界，说明该问题不限于39题。

## 离线对照方法

新增`eval/kb/audit_rerank_ties.py`：分数不同时仍按降序，**只有数值完全相等时才使用原混合召回次序**。不设阈值、不做四舍五入、不将近似分数视为相同，也不读取金标决定排序。

只使用dev，保留原结果文件及哈希；输出另存为`offline_exact_tie_counterfactual`。复用`eval/kb/score_rerank.py`评分。本轮候选池未变、模型未重跑，因此下表的同分方案为反事实重算，不是新增模型实测。
