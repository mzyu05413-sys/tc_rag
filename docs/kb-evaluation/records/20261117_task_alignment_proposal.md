# 评测任务与生成主线对齐提案

状态：基于2026-11-17用户讨论的建议，未获授权实施主线改造；未修改代码、默认配置、标签、快照或模型调用。

进一步的代码审查、整改优先级和企业试点门槛见[架构评审与调优方案](../architecture_review_and_optimization.md)。该文档是本提案的详细展开，仍不表示方案已实现。

## 问题判断

已有5/30题及新10题主要是需求规则/事实问答，不能直接等同于功能点或测试点，也不能以其指标证明测试点和用例生成质量。已有排序、同分、删除线发现依然可用，但结论范围是相应问答输入下的检索行为。

用户最终关注的任务应明确为：围绕指定功能及测试任务，最终提供给生成模型的上下文是否完整、准确地包含所需需求依据。当前库只有六份PRD，未纳入已审核历史测试点、用例或缺陷，不能将其称作历史测试经验库。

## 代码核对

- `domain/models.py`已存在Feature，保存feature_id、name、description、evidence_ids；RequirementRule通过feature_id引用它。无需再平行增加一套功能点对象。
- `Pipeline.plan_batch`当前以instruction与一批rule.statement组装检索查询；rule_batches当前按连续规则切片，未显式按feature_id分组。
- `Pipeline._generate_batch`当前以一批point.objective查询，但核心上下文已经补齐这些点所属功能的规则与证据。细测试点不会自动导致上下文只含一个字段。
- `Pipeline._supplement`在预算约束后保存实际采用/省略的补充证据，适合作为应用层评测挂接点；完整输入包括request中的核心evidence及最终supplemental_evidence。
- 原RagContext检索单位为EvidenceSpan（包括原文来源切片）；独立KB评测以Chunk为单位。底层能力复用不等于索引单位、查询、范围和最终上下文相同，不能直接互换报告结论。

## 推荐方案

1. 功能任务作为主评测输入，例如“围绕订单状态管理准备测试设计所需的规则依据”，包含功能边界、操作、角色及场景。不要只有笼统模块名，也不要把金标答案拼进人为编写的查询。
2. 规则事实题保留为诊断回归，测试点级查询继续用于用例阶段的条件/边界补充。不同层级结果分层报告，不用换宽问题后的更高P证明算法改善。
3. 优先按现有Feature组织规则及规划批次。考虑查询包含功能名称/描述、当前任务、规则或测试点目标，并保持最终细化到TestPoint的引用关系。新策略显式启用，保留原入口默认语义。
4. 首先在真实流程的上下文组装末端增加独立评测适配，复用生产路径，不实现第二套检索。评测是旁路观察/回放工具，不是每次生成必经的评分阶段。
5. 若后续确认细片段缺上下文，再考虑子片段匹配、父章节/功能上下文补齐；父级内容保留原始来源、作废区间和预算，摘要不能成为无原文支持的新规则。

## 指标与归因

主表固定评估预算裁剪后实际提供的证据上下文。片段/来源单元全集固定且相关性完整审核时，统计标准TP/FP/FN/TN、P/R/F1及宏微平均；改变切分或证据单位后不得直接沿用旧片段标签。另以必要规则为单位统计证据覆盖率，不能将事实级覆盖率与片段精确率合成标准F1。

直接证据和额外检索贡献分开记录：核心证据已覆盖什么、检索新增覆盖什么、最终缺什么。直接绑定的原文不是检索召回功劳。所有结果保持同一来源区间、文档版本和快照可追溯。

中间阶段保留候选及来源轨迹用于归因：解析遗漏、范围排除、候选预算截断、融合/重排后移、上下文去重/裁剪、最终生成未使用证据。正式得分表不需要列成多轮独立组件竞赛，但不能因只看最终输出而丢掉中间诊断。

## 分步实施建议

| 阶段 | 工作 | 门槛 |
|---|---|---|
| A 任务定义 | 挑选少量有明确范围的功能任务，说明规划和用例生成分别需要什么证据；旧问答标记为诊断集 | 用户确认业务任务和评测边界 |
| B 金标与观测 | 按功能任务建立必要规则清单和来源；读取实际核心+补充上下文，按来源去重归一 | 未审核集合不计算正式Recall；不归功于检索的直接证据单列 |
| C 配对实验 | 同一任务/金标/范围/预算，对比现行查询与功能信息增强查询；保留细规则反例 | 新题只在策略冻结后使用；不同时改切分、k及rerank造成混杂 |
| D 应用效果 | 验证必要规则是否转化为测试点和有依据的步骤/预期 | 单列生成质量，不以检索P/R替代 |

新10题仍是pending问答候选，暂不发布为业务主评测金标，不删除原材料。此提案不自动授权以上改造或真实模型调用。

## 公开参考与可借鉴范围

- [LangSmith RAG evaluation](https://docs.langchain.com/langsmith/evaluate-rag-tutorial)：分别评估检索相关性、回答正确性及依据一致性，可借鉴结果与组件诊断并存的思路，不意味着一定使用LLM裁判。
- [LlamaIndex Auto Merging Retriever](https://developers.llamaindex.ai/python/framework/integrations/retrievers/auto_merging_retriever/)：子节点检索后按父子关系合并上下文，适合作为后续上下文补齐参考；不是本项目已实现能力，也不保证指标提高。
- [RAGTAG工业研究](https://arxiv.org/abs/2404.12772)：从需求生成测试场景，在工业项目中结合相关性、覆盖、正确性、连贯性、可行性开展专家评价。可借鉴任务级验证，而非只比较检索指标；它未证明所有框架必须以功能名检索。
- [Ragas Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)：支持按参考答案中的主张衡量上下文覆盖。该口径不同于标准片段Recall，需独立命名和汇总。
