# R0～R3 精简评测方案评审

本轮仅评估方案，未改生产检索语义，未调用模型。建议采用 R3 指标验证、R0 冻结底座、R1 模式对照、R2 后端对照的顺序，问答、干扰和 Vision 正式对照暂不纳入本轮。

## 必须修正

候选相关数 C 与去重命中的必要证据单元数 U 是不同计数。一个候选可覆盖多个证据，也可由多个候选重复覆盖同一证据，不能共用一个 TP 来推导分类式微平均。

每题 P=C/k，R=U/G。宏平均分别平均每题 P、R 和两者调和平均。微汇总使用 P=sum(C)/sum(k)、R=sum(U)/sum(G)，再按已声明定义计算综合 F1。保留 relevant_candidates、covered_groups、total_groups、k，不把候选 FP 和证据 FN 混成同一混淆矩阵。用户三题算例在 C=U 的特例下数值成立，不能作为通用证明。

固定 k 且使用同一有效问题集合时，宏、微 Precision 相同。无答案、未知或失败题按预登记口径单列，不能把各指标的不同可评分集合直接混在一起。

## R1

在 eval/kb 中编写薄 harness，复用原组件。使用相同快照、问题、范围、k 和候选预算，关闭重排。关键词索引构建与稳态查询分别计时；固定查询向量可避免重复付费。精确术语、语义改写和多证据问题分层，预期方向属于待验证假设。nDCG 仅在完整候选级相关标注可确定时计算。

## R2

代码核对确认当前 FAISS 每次查询重建范围内 IndexFlat，并在查询前调用 metric.score 对全部范围向量进行 NumPy 打分校验。这条路径同时含复制、float64 转换、完整打分和 native 重建。NumPy 使用 stable argsort 完整排序，也计入适配器路径。

适配器端到端与预构建 native 内核两条路径分别报告。Flat 的精确检索也可能有 SIMD、批处理和实现层面的收益，不以近似索引作为 FAISS 价值的唯一来源。

主质量数据使用当前快照真实维度。合成 1k/10k/100k 仅测性能，按机器内存逐档开启。理论向量字节与进程峰值内存分开。结果按 ID 对齐分数，以预登记容差处理 float32/float64 差异和边界并列。

参考 https://github.com/facebookresearch/faiss/wiki/Implementation-notes 和 https://github.com/facebookresearch/faiss/wiki/Faiss-indexes ，2026-11-12 核对。

## 当前边界

现有问答实现保留，本轮不继续扩展或纳入正式对照。当前 score_retrieval 无 F1 或独立微汇总，需要在指标口径确认后补充；当前 SearchService 无纯关键词模式，优先由独立实验 harness 组合已有算法。
