## 3. 第一步：审核分块是否保留完整含义

对着需求原文阅读试分块。段落、表格和图片解释的来源以材料中的 Block、章节与 Locator 回查；字符区间 `[a,b)` 表示从 a 到 b 之前，索引从 0 开始。

|检查项|可以接受|需要记录的问题|
|---|---|---|
|原文与顺序|文字、否定词、数值、单位和来源都保留，顺序可解释|漏字、改写、串页、丢否定或定位错误|
|章节归属|标题对应本章或下级正文，兄弟章节不误挂|上一章标题挂到下一章、无依据跨章合并|
|原子需求|一条“条件＋行为/约束＋例外”尽量完整落在一个 Chunk|只有结果没有适用条件，或例外被拆到其他 Chunk|
|长段|按完整句组织；不可拆长句保留并告警|句子无说明被截断，或长段中部实际丢失|
|表格|行完整，表头和列关系能回查；重复表头有明确来源|数据行错当表头、行被截断、列错配或未知表头被当成事实|
|重叠|重复内容来自同一原文范围，对指代理解有帮助|重复片段脱离条件、来源错位、误将重复算成新增需求|

**同一条完整需求不等于同一段文字。** 一段可能有多条独立约束，一条约束也可能需要多个段落或表格行共同支撑。

例如虚构需求“仅管理员可以提交；但已归档记录不可提交”：不能只保留“可以提交”，遗漏角色或归档例外。若条件与结果分属多个 Chunk，即使第二步背景里都能看到，也不能直接认定“单 Chunk 边界完整”。

不必把全部 96 个大 PDF Chunk 逐字审核才能反馈。先完成下文的 12 项候选，并重点抽看章节交界、长段、表格和风险 Issue；如果只做抽样，结论写“抽样通过”，不能写“全文语义通过”。发现系统性问题后，扩大到同类位置检查。

## 4. 第二步：审核正文与背景是否分清

打开 `extraction_context.md`，每个 Chunk 都分为两部分：

- **可引用正文**：只有这些 `allowed_sources` 区间允许作为当前提炼的证据。
- **仅作背景**：同 Block 的其他区间，或相邻 Block；帮助理解指代、发现条件与冲突，不能直接成为新增确定规则的依据。

你主要看四点：

1. “该字段、上述操作、但是、除外”等表达附近，是否提供了正确的前后文。
2. 背景是否来自同一文档；跨章节的内容是否真的相关，是否容易误套到当前规则。
3. 标为局部的背景有没有恰好截掉“不、仅、除外、当……时”等关键条件。截取虽被明确标记，仍可能不利于理解，应记录。
4. 如果一条规则必须引用背景才成立，记为“需要调整边界或联合提炼”，不要用“背景里已经有了”判定解决。

特别说明：

- `scope=same_block` 仍是背景。Block ID 相同不代表可引用其他字符区间。
- 这是**字符窗口预览，不是实际模型请求**。正式请求还包含完整原始 Block、指令、提示词与 Schema，预算不足时可能删去背景。
- 原文完整 Block 原本就会随请求提供。第四批强调的是显式窗口与授权隔离，不能据此声称此前模型完全看不到这些文字。
- 三份历史样本中没有真实 `between` 空隙背景案例；该路径只有合成表格测试，真实复杂表格效果仍待验证。

## 5. 第三步：审核 36 项候选，填写反馈表

三份文档各 12 项，两种策略共用同一组候选，**总共只需审核 36 项，不用重复标注**。

打开对应的 `gold_review.md`，按候选 ID 在[反馈表](../../workdir/diagnostics/chunking/fourth_batch_20261104/review_feedback.md)记录。先判断候选本身是否适合评估，而不是看到原文正确就直接判定通过：

|候选情况|反馈表填写|后续标注处理|
|---|---|---|
|确实是一条条件、行为、例外完整的可测试约束|确认完整单元|可转为 confirmed|
|一个候选含多条独立约束|需拆分；说明拆分点|拆成唯一 ID 与各自准确来源后再确认|
|缺少条件、前指对象或例外|需补充来源；指出对应位置|补全同文档的来源区间后再确认|
|纯格式、重复表头等，不是独立测试约束|排除；写明理由|excluded|
|暂时无法判断或图片含义未核实|待定；写明疑问|保持 pending|

页面展示本身可以是有效需求，不能一律排除。候选中出现 vision 资料时，确认“这是完整的评估单元”不等于批准图片解释为业务事实。

**你可以只填反馈 Markdown，不必编辑 JSON。** 把反馈表位置或结论发给我后，我再根据你的明确判断整理派生标注；不自动把全部 pending 改为 confirmed，不覆盖原候选文件。需要补充/拆分的来源不明确时仍保留待定。

如果你习惯直接改 JSON，则复制 `gold.review.json` 为私有 `gold.confirmed.json`；保留 `run_id` 与 `block_fingerprint`。`quote` 必须逐字等于来源区间；改引文必须同步改范围。只改阅读版 Markdown 不会自动更新评分文件。

## 6. 第四步：看指标，判断能否进入真实模型验证

目前以 target=900、overlap=100 作为统一阅读样本，**不代表已证明它是最优参数**。预算网格只有分块对照，不含对应的新一轮模型提炼结果。

|指标或现象|本次怎么判断|
|---|---|
|原文字符/数据行覆盖|结构底线是 100%；三份历史样本已通过。不能替代语义判断|
|合法来源、正文可重建、同输入稳定 ID|结构底线必须通过；已由离线检查覆盖|
|超预算 Chunk|不能静默截断，必须有风险 Issue；完整长句/行超限不自动等于实现失败，但需确认后续请求能否容纳|
|抽样边界完整率|已确认原子需求完整落在单个 Chunk 的数量 ÷ 已确认单元总数；未确认时为 null。只代表这组抽样|
|跨多个 Chunk 联合覆盖|表示文字仍在，但单块提炼可能缺完整依据；不能冒充边界完整|
|相邻重叠率|只比较同文档、同章节的有效相邻块。无需强制达到 80%，不能靠重复更多证明质量更好|
|纯标题/小碎块数量|结合归属判断；减少低价值请求有意义，但不能为减少数量挂错章节|
|本地毫秒与 Chunk token|仅反映本次离线分块及文字量，不是全流程耗时、模型输入 token 或费用|

审批评论的 0 个同 Block 背景属于正常结果：该参数下没有相应需要补充的同 Block 片段，不代表第四批失效。PDF 超预算数变少也不能单独证明质量改善，新策略停止注入未确认的续表表头是其中一个原因。

这次不擅自制定“95% 边界完整率”等硬性业务指标。先完成同一份标注，再公平比较两策略与参数；人工可接受线和真实模型预算待后续确定。

## 7. 怎么记录问题与给出结论

每个问题至少包含：样本、Chunk/候选 ID、Block 与区间或章节定位、实际现象、原文应有含义、影响。截图可以补充，但不要只写“感觉不合理”。问题统一写进[反馈表](../../workdir/diagnostics/chunking/fourth_batch_20261104/review_feedback.md)，无需改多个文档。

|级别|例子|对本轮结论的影响|
|---|---|---|
|阻塞|原文丢失/改写、来源错位、串文档、标题误归属、数据行损坏、引用越权|修复后复核，不能判定该范围通过|
|需修正或确认|条件例外被拆散、背景缺关键前指、表头或列关系不清|指出具体单元；明确修复或接受受限范围，不能归入无问题|
|观察项|碎块较多、重复背景较多、预算可能不合适|留作调参依据，不直接当成功能失败|

你最终回复以下四项即可：

```text
审核范围：三份样本抽样 / 指定章节 / 全文（按实际填写）
结论：通过抽样审核 / 有条件通过 / 需要修复 / 尚未完成
问题记录：反馈表路径及未解决条目
参数倾向：维持现状 / 候选策略与预算 / 暂不决定
```

“抽样审核通过”表示可以讨论下一轮验证，不等于自动切换正式配置或授权付费调用。
